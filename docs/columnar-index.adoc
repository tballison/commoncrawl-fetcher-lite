= Option B: Querying the Columnar Index
:toc: left
:toclevels: 2

The `Fetch` command (xref:configuration.adoc[Configuring the Fetch]) finds matching files by
downloading and scanning the raw CDX index shard-by-shard -- reliable and needs nothing but
HTTPS, but it means downloading roughly 300GB of index data *per crawl*, regardless of how
rare your target file type is. For a single crawl that's ~4 hours; for five crawls, most of a
day.

`QueryIndex` is an alternative command that finds the same matches by querying Common Crawl's
https://commoncrawl.org/columnar-index[columnar index] -- the same metadata as the CDX index,
pre-converted to partitioned Apache Parquet. Column and partition pruning mean a targeted query
touches a small fraction of that 300GB, and it can search *every* available crawl in one query
instead of one crawl per run. In testing against `CC-MAIN-2026-30` (already fully scanned via
`Fetch` in ~4 hours), the equivalent `QueryIndex` run found the same files -- plus 3 more that
the CDX scan's line-oriented parser had missed -- in about 2 minutes.

WARNING: This is still the newer of the two paths. `Fetch` remains the default recommendation
for straightforward, unattended, credential-free runs; reach for `QueryIndex` when you want
speed, broader crawl coverage, or already have AWS credentials on hand.

CAUTION: A `crawlGlob` spanning *every* crawl (`CC-MAIN-*`, ~125 crawls) touches thousands of
Parquet part-files and can trigger S3 request-rate throttling (`503 SlowDown`) on a sustained
run. `QueryIndex` widens DuckDB's default HTTP retry budget specifically to survive this (see
<<Retry tuning>>), but an empirical test of an unbounded `CC-MAIN-*` glob using DuckDB's stock
retry settings ran for 97 minutes before failing outright to a `SlowDown` error with zero
partial results retained. Prefer scoping `crawlGlob` to the crawls you actually need
(`CC-MAIN-2026-*`, or an explicit range) over `*` when you can.

== Prerequisites

You need *AWS credentials* -- any valid AWS account, nothing Common-Crawl-specific. This is
*not* AWS Athena, and no Athena charges apply.

Why credentials are needed at all: Common Crawl's S3 bucket allows anonymous `GetObject` (that's
how `Fetch` and the rest of this tool work with zero AWS setup) but not anonymous
`ListBucket` -- you can download a file if you already know its exact name, but can't ask "what
Parquet part-files exist under this crawl's partition?" without being a signed-in AWS caller.
That's the one operation `QueryIndex` needs credentials for.

This should not cost you anything: the bucket is *not* requester-pays (confirmed via
`https://commoncrawl.s3.amazonaws.com` bucket policy and Common Crawl's own documentation), so
S3 request/storage costs are borne by Common Crawl's AWS Open Data sponsorship, not by whoever's
credentials sign the request. `QueryIndex` uses your default AWS credential chain (the same
resolution DuckDB's `load_aws_credentials()` uses -- environment variables, `~/.aws/credentials`,
etc.), so if `aws configure` already works on your machine, you're set.

If you'd rather run the equivalent query server-side, the underlying Parquet files are also
queryable from Amazon Athena -- see the
https://github.com/commoncrawl/cc-index-table[cc-index-table] project for the Athena
`CREATE TABLE` statements. That path *does* bill (~$5/TB scanned, typically well under $1 for a
column-pruned single-crawl query); `QueryIndex` does not use it.

=== Retry tuning

DuckDB's httpfs defaults (`http_retries=3`, `http_retry_wait_ms=100`, `http_retry_backoff=4`)
give well under 2 seconds of total backoff on a failed HTTP read -- fine for a handful of
files, not enough to ride out sustained S3 throttling on a broad query. `QueryIndex` and
`CountIndex` widen this before running any query: `http_retries=12`, `http_retry_wait_ms=2000`,
`http_retry_backoff=1.5`, i.e. waits of 2 s growing to ~3 min, ~9 min in total per failed read.
Override with `-Dcc.duckdb.httpRetries`, `-Dcc.duckdb.httpRetryWaitMs` and
`-Dcc.duckdb.httpRetryBackoff` (1-10). The earlier backoff of 2 allowed ~2.3 h on one request:
on 2026-11-05 a single SlowDown near the end of a scan parked queries for an hour or more with no
sockets open, which looked like a hang. Better to fail in minutes and rerun when S3 is quieter.
These are separate from `BackoffHttpFetcher`'s ladder for WARC fetches. This is
not a substitute for scoping `crawlGlob` sensibly -- it buys patience, not throughput.

[[rate-limiting]]
=== Rate limiting: if everything is slow, check for 503 SlowDown

If every query (or fetch) is slow, check the log for `503`/`SlowDown`. It is Common Crawl's
per-IP rate limiting, asking you to reduce your request rate. On 2026-11-04 a laptop got 503
SlowDown on every request to data.commoncrawl.org and S3 for hours, while the widened retries
above made queries merely look slow (120-340 KB/s). Stop, wait (hours), then resume at a lower
request rate (`-Dcc.duckdb.threads=1`, Fetch `numThreads` 1). Do not switch to another host or
IP to get around it: that routes around the limit Common Crawl is asking you to respect.

What the tool does about it:

* *Preflight.* Before `QueryIndex`/`CountIndex` open DuckDB, they HEAD
  `crawl-data/<crawl>/cc-index-table.paths.gz` on data.commoncrawl.org and on S3 (a fixed older
  crawl when `crawlGlob` is a wildcard; the Parquet glob's own files can't be HEADed without a
  list call). A 503 or 429 logs an ERROR banner and fails fast. `-Dcc.preflight=false` skips it.
* *During the query.* DuckDB 1.3's logging records every HTTP attempt, retries included. A side
  connection polls it every 30 s; each 503/429 is logged at WARN, and 5 within 60 s log the ERROR
  banner and cancel the query. The end of the query logs DuckDB's request count and 503/429
  retries (WARN when non-zero), and `manifest.json` records them under
  `rate_limited.duckdb_requests` / `duckdb_by_status`. DuckDB 1.3 has no call to truncate its
  in-memory log, so every 20,000 entries the counts are banked and the log is cleared by switching
  its storage (requests in that instant are not counted); a crawl-wide scan stays countable.
  Caveat (2026-11-05, in-region over `s3://`): DuckDB sat in httpfs retry backoff (no open sockets,
  a worker in `nanosleep`) while an `aws s3api get-object` on the same prefix got SlowDown, and
  these stats logged no 503s. Until that is explained, treat a query that stops reading with no
  sockets open as rate-limited.
  `-Dcc.duckdb.httpStats=false` turns this off.
* *WARC/CDX fetches* (`BackoffHttpFetcher`, the default HTTP fetcher) log each 503/429 at WARN
  with the host and a running count. 5 within 60 s log the ERROR banner and pause all HTTP
  fetches in the process for 10 minutes, doubling on each later trip (capped at 24 h), instead
  of the normal `throttleSeconds` ladder. The run summary and `manifest.json`
  (`rate_limited.http_total`, `http_by_status`, `by_host`, `pauses`) give the totals.
* *S3 WARC/CDX fetches* (`fetcher.profile`, `BackoffS3Fetcher`) feed the same process-wide
  monitor: an S3 503 SlowDown or 429 (found anywhere in the exception's cause chain) is counted
  under host `s3://commoncrawl`, and every fetch thread waits out a pause before its next request,
  so one thread's 503s pause all of them. The wrapped Tika `S3Fetcher` makes one attempt per call;
  `throttleSeconds` is the retry ladder. In-region on 2026-11-05: 16 fetch threads drew ~30
  SlowDowns/min, 8 and 4 each tripped the pause within a minute, 2 ran without one. Start at 4 and
  halve on a pause.

The banner:

----
Common Crawl is rate-limiting this host (503 SlowDown): N in 60 s. Stop and wait (hours), then
resume at a lower request rate (DuckDB threads=1, Fetch numThreads=1).
----

=== Bandwidth: threads and pruning

Each DuckDB thread issues its own S3 range reads, and DuckDB defaults to one thread per core, so a
scan that can't skip data will saturate a home or office link. `-Dcc.duckdb.threads=N` sets
DuckDB's `threads` (default: unset, i.e. all cores); `-Dcc.duckdb.memoryLimit` (default `4GB`)
caps memory. `numThreads` in the config is the WARC fetch pool and does not affect the scan.

The index is sorted by `url_surtkey`: each row group covers one contiguous SURT range, so
`url_host_tld` min/max statistics let DuckDB skip row groups. A predicate bounded to one TLD
(`url_host_tld = 'gr'`) reads a small fraction of a crawl: measured on CC-MAIN-2026-43, `cy` read
110 MB vs ~83 GB for a full scan of the same columns. Adding a `url_surtkey` range prunes no
better and costs extra reads of that wide column, so bound on `url_host_tld` alone. Predicates on `url_path`, MIME or a hash sample cannot be
skipped this way; with no TLD bound they read the needed columns for the whole crawl. Run one
query per TLD (AND-only bounds) rather than one OR across many TLDs, and check the cost on a
small TLD with `CountIndex` first.

== Config

[source,json]
----
{
  "dryRun": false,
  "columnarIndex": {
    "crawlGlob": "CC-MAIN-2026-*",
    "subset": "warc",
    "where": "content_mime_detected LIKE 'application/onenote%' AND fetch_status = 200"
  },
  "docs": {
    "path": "/home/you/data/commoncrawl/onenote"
  },
  "targetPathPattern": "xx/xx/xxx"
}
----

[cols="1,3"]
|===
|Field |Description

|`crawlGlob`
|Which crawl partition(s) to query, e.g. `CC-MAIN-2026-30` for one crawl,
`CC-MAIN-2026-*` for all 2026 crawls, or `*` for every crawl Common Crawl has. Interpolated
directly into `s3://commoncrawl/cc-index/table/cc-main/warc/crawl=<crawlGlob>/subset=<subset>/`.

|`subset`
|Optional, defaults to `warc` (the response-record subset; matches what `Fetch` scans by
default).

|`where`
|A raw SQL `WHERE` clause evaluated against the Parquet columns (see <<Column reference>>
below) -- there's no selector-DSL translation layer, so write it directly. This is the same
predicate a hand-written DuckDB or Athena query would use.
|===

All the usual top-level fields still apply: `docs`, `fetcher`, `dryRun`, `extractTruncated`,
`maxFilesExtracted`, `maxFilesTruncated`, `targetPathPattern`, `runLabel`. `recordSelector` is
not used in this mode -- filtering happens in the SQL `where` clause instead, which DuckDB pushes
down into the Parquet scan itself rather than re-checking every row in Java.

== Running it

[source,bash]
----
java -jar commoncrawl-fetcher-lite-X.Y.Z.jar QueryIndex config.json
----

Each matched row is fetched and logged exactly like a `Fetch` match -- same WARC byte-range
fetch, same `logs/<runLabel>/extracted-urls.csv` / `urls-truncated.csv` output (see
xref:configuration.adoc#_logging[Logging]), so `QueryIndex` and `Fetch` results accumulate into
the same files if you point them at the same `docs.path` / `runLabel`.

== Counting before fetching (CountIndex)

`CountIndex` runs a GROUP BY count query you supply and prints the result as a tab-separated
table; it never touches a WARC. Put the query in `columnarIndex.countQuery`; `${parquet}` is
replaced by the `read_parquet(...)` source for your `crawlGlob`/`subset`, and `where` is not
needed. `countTimeoutSeconds` (default 1800) cancels a runaway query.

[source,json]
----
{
  "columnarIndex": {
    "crawlGlob": "CC-MAIN-2025-08",
    "countQuery": "SELECT content_charset, count(*) AS n FROM ${parquet} WHERE fetch_status = 200 AND content_mime_detected = 'text/html' GROUP BY 1 ORDER BY n DESC LIMIT 30",
    "countTimeoutSeconds": 900
  }
}
----

[source,bash]
----
java -jar commoncrawl-fetcher-lite-X.Y.Z.jar CountIndex count.json
----

== Provenance and run manifest

Every successful extraction (`Fetch` and `QueryIndex`) appends one JSON line to
`logs/<runLabel>/provenance.jsonl` (override with top-level `provenancePath`): all index
fields (`url`, `mime`, `mime_detected`, `status`, `digest`, `length`, `offset`, `filename`,
`charset`, `languages`, `truncated`, `redirect`), `crawl_id` (from the WARC filename),
`sha256`, `stored_length`, `output_path`, and `http_headers` (every HTTP response header from
the WARC record, name to list of values). A payload that recurs under several URLs is stored
once but gets one line per URL. `redirect` is not in the columnar index and is null on
`QueryIndex` runs.

`logs/<runLabel>/manifest.json` (override with `manifestPath`) is written at start and
rewritten at the end: the config verbatim, `seed`, tool git commit, start/end times, counts
(including files written per `mime_detected|charset`), and `rate_limited` (503/429 counts; see
"Rate limiting" above).

== Seeded sampling

Top-level `seed` seeds every `sample` fraction in `recordSelector`. If omitted, a seed is
generated and recorded in the manifest (`seed_generated: true`). Results are reproducible only
for a single-threaded run over the same input order (`numThreads: 1`).

== Column reference

Common columns for the `where` clause (full schema:
https://github.com/commoncrawl/cc-index-table/blob/main/src/main/resources/schema/cc-index-schema-flat.json[cc-index-schema-flat.json]):

[cols="1,3"]
|===
|Column |Description

|`url` |Full URL
|`url_host_tld` |Top-level domain, e.g. `com`, `org`
|`url_host_registered_domain` |Registrable domain, e.g. `example.com`
|`fetch_status` |HTTP status code (integer, not a string -- e.g. `fetch_status = 200`)
|`content_mime_type` |Content-Type from the HTTP header
|`content_mime_detected` |MIME type as detected by Apache Tika
|`content_digest` |SHA-1 content digest
|`content_charset` |Declared charset
|`content_languages` |Declared language(s)
|`content_truncated` |Non-null if Common Crawl truncated the capture (5MB limit)
|`warc_filename` |WARC filename/path below `s3://commoncrawl/`
|`warc_record_offset` / `warc_record_length` |Byte range of the WARC record
|===

Sample predicates:

[source,sql]
----
-- by mime type
content_mime_detected LIKE 'application/onenote%' AND fetch_status = 200

-- by extension, when mime detection might miss it -- filter on url_path, NOT the full url:
-- ".one" is also a real gTLD, so "url LIKE '%.one'" matches bare domains like
-- "http://chernivtsi.one" (no path) as false positives. url_path excludes the host, so a
-- domain-only URL's path is empty/"/" and won't match here.
(url_path LIKE '%.one' OR url_path LIKE '%.onetoc2') AND fetch_status = 200

-- by domain
url_host_registered_domain = 'example.com' AND fetch_status = 200
----

== Why results can differ from `Fetch`

`Fetch` parses CDX lines with a hand-rolled `sortkey timestamp {json}` splitter
(`CCIndexRecord.parseRecord`) that can fail on malformed or unusual lines -- and Common Crawl
has, in practice, added new JSON fields to the CDX format between crawls (see
`@JsonIgnoreProperties(ignoreUnknown = true)` on `CCIndexRecord`) that older parsing logic
wouldn't have tolerated. The columnar index is proper structured Parquet with no such parsing,
so `QueryIndex` results are generally a superset of what `Fetch` finds for the same crawl and
predicate, not a different sample.

== Prior art

The query-columnar-index-then-range-fetch-the-WARC-record pattern `QueryIndex` implements isn't
novel -- Common Crawl Foundation's own tutorials walk through the same two steps by hand:

* https://github.com/commoncrawl/whirlwind-java[whirlwind-java] -- a Java walkthrough covering
  CDXJ vs. columnar indexes, reading WARC records with
  https://github.com/netpreserve/jwarc[jwarc] (the same library this project uses), and a task
  titled "Query using the columnar index + DuckDB from outside AWS" followed by range-fetching
  the match. It's a single hardcoded illustrative example (one URL, one timestamp) meant to be
  read and adapted by hand, not a config-driven batch tool -- no crawl/mime selection, no
  structured output logging, no retry handling, no truncation handling, no bulk operation
  across many matches. `QueryIndex` is what running that pattern unattended, at scale, against
  a config file looks like.
* https://github.com/commoncrawl/whirlwind-python[whirlwind-python] and its announcement,
  https://commoncrawl.org/blog/announcing-the-whirlwind-tour-of-common-crawls-datasets-using-python[Announcing
  the Whirlwind Tour of Common Crawl's Datasets using Python] (June 2025) -- the same pattern
  in Python, using `warcio`/`cdxj-indexer`/`cdx_toolkit`/`duckdb`.
